The receipts — making the patent moat tactile.

A pure function is reproducible. But the user can't see that without a signal. The "run signature" turns reproducibility into something an auditor can hold.

Like a chess game's PGN notation

In chess, every move history is a string: 1. e4 e5 2. Nf3 Nc6 .... Two players, anywhere in the world, can replay the exact same game from the notation. The notation IS the proof.

Our run signature is the same idea. It's a SHA-256 fingerprint of the inputs that produced a score. Two assessments with the same fingerprint MUST have produced the same score, because the math is deterministic and the inputs are bit-identical. The hash is the chess notation of an ERM score.

What goes into the signature?

responses 100 (questionId, score) pairs, sorted by id. Notes and evidence filenames are excluded — they don't change the score.
catalogHash Hash of the question catalog itself. If a question text changes or a weight is tweaked, this differs.
catalogVersion Human-readable bump (e.g. 1.0.0). Lets us evolve the catalog while keeping comparisons safe.
scoringSpecVersion Bumped when the scoring math itself changes. 1.0.0 today.
⚠️
Notice what's NOT in the hash

The current time. The operator's email. The browser. The IP address. The database row creation timestamp. None of those affect the score, so none of them belong in the signature. Including them would be lying to the auditor.

Why two hashes, not one?

CODE · shared/signatures.ts 
// Hash 1: the score itself
const scoringInputHash = sha256(canonicalize({
  responses: /* sorted, only q+s */,
  catalogHash, catalogVersion, scoringSpecVersion,
}));

// Hash 2: the analysis VIEW
const analysisHash = sha256(canonicalize({
  scoringInputHash,
  benchmarkType,           // target / industry / peer
  benchmarkProfile,        // the actual numbers
}));
PLAIN ENGLISH

Hash 1 — scoringInputHash — the fingerprint of "these answers, scored by these rules." It does NOT change when you switch benchmark.

Hash 2 — analysisHash — the fingerprint of "this score viewed against this benchmark." It DOES change when you toggle Target → Industry on Today.

This separation matters. An auditor can ask "did the score change between Q1 and Q2?" — answer: compare scoringInputHash. The analyst can ask "did the relative gap change?" — answer: compare analysisHash. Two questions, two receipts.

The contract is pinned in tests

The signature isn't a vibe — it's enforced by the test suite. tests/signatures.test.ts contains assertions that close the loopholes:

order-independence Shuffling the response array must not change the hash.
score-sensitivity Changing one answer must change the hash.
benchmark-isolation Switching benchmark changes analysisHash but NOT scoringInputHash.
coverage-rejection A response set with 99 valid + 1 fabricated questionId must reject.
range-rejection A score outside 1–5 (or non-integer) must reject.

If any of these break, CI fails the PR. The reproducibility claim is therefore enforceable: it's not a thing engineers promise, it's a thing tests check.
