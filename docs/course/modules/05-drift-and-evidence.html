Drift and evidence — what changed, and what backs it up.

A score by itself is a vibe. A score plus "this changed since last time" plus "here's the document" is an audit trail.

Drift = a doctor's vital-sign chart

A doctor doesn't ask "is the patient healthy?" — they ask "what changed since last visit?" Single readings are noise; trajectories are signal. Same with risk maturity.

The Live Brief headline on Today is always one of three forms — generated automatically from the drift comparison:

📉

Critical regression

"Risk Treatment regressed −1.00 on Generation since the prior assessment." Coral severity stripe. severity: 'CRITICAL' when |delta| > 0.5.

📊

Drifting, not critical

"Generation is drifting on 6 of 10 pillars vs Industry." Amber stripe. Worth looking at, not screaming.

✅

On benchmark

"Generation is on benchmark across 8 of 10 pillars." Mint stripe. Celebrate, but stay vigilant.

"Prior assessment" is operator-scoped — and that fact is the difference between an audit-grade product and a prototype

CODE · api/assessments/[id]/analysis.ts 
// Find the prior COMPLETED assessment for the same operator,
// same entity. NOT just "same entity any operator".
const [prior] = await sql`
  SELECT id FROM assessments
  WHERE "entityId" = ${assessment.entityId}
    AND id != ${id}
    AND "createdAt" < ${assessment.createdAt}
    AND status = 'completed'
    AND "operatorEmail" = ${assessment.operatorEmail}
  ORDER BY "createdAt" DESC LIMIT 1
`;
PLAIN ENGLISH

Find the previous version of THIS Generation assessment, by THIS operator, that was actually finalized.

The operatorEmail filter exists for a real reason: without it, Operator B's drift headline could compute against Operator A's data. We caught that during an audit and shipped the fix the same day.

The status = 'completed' filter excludes drafts and abandoned attempts. Drift only compares to finalized snapshots — not "I-was-just-experimenting".

"id != current" prevents self-comparison (drift would be 0 across the board, useless).

🚨
Cross-tenant data bleed: the silent killer

The original version of this query missed the operatorEmail filter. It looked harmless. It also silently leaked one operator's risk posture into another operator's headline. Multi-tenant SaaS lives or dies on this kind of filter. Every database query in this product that reads operator-scoped data is audited for this exact pattern.

Evidence — the audit-grade attachment story

An auditor's first question after seeing a score: "show me the document that backs question 47." If the answer is "we don't store it," the score is hearsay. So we store every uploaded file in a private bucket with three guarantees:

private bucket No public listing. No public URL. The only way in is a signed link our function issues.
10 MB / file cap Server-side rejection of larger uploads — saves bandwidth, fits ERM evidence shape (PDFs, Excel, screenshots).
MIME allowlist PDF, XLSX, DOCX, common images, plain text. Bucket itself rejects anything else, regardless of what the file extension says.
5-min signed URLs Download links expire in 300 seconds. Even if a link leaks via screenshare, it's stale by the time anyone tries.
deterministic key {assessmentId}/{questionId}-{filename}. One slot per (assessment, question). Re-uploads overwrite the slot — by design, since responses only carry one filename column.

Why this dance

The service-role key can do anything. If it ended up in a browser bundle, the whole evidence locker becomes public. So the function holds the key, mints a 60-second-window upload URL, and hands ONLY that URL to the browser. The browser uploads directly to Storage — fast, no proxying through the function. Same pattern for downloads, with a 5-minute window.
