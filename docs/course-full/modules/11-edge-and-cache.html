Edge and cache — the quiet 80% of "feels fast."

The score is deterministic. Which means the answer is cacheable. Which means we can make the second click feel free — without ever serving stale data to the wrong operator.

A library reading room, not a vending machine

A vending machine recomputes from scratch every time. A library hands you a copy from the shelf, and only goes to the basement when the catalog says the shelf is empty.

Our edge is the reading room. Vercel's CDN sits in front of every API route. The function tells it — per response — how long the answer is good for, who can share it, and whether to revalidate in the background. Module 5's hashes make this safe: the same input always produces the same output, so caching can never lie.

3 cache policies, named for what they actually do

CODE · api/_lib/cache.ts 
export const shortPublic =
  'public, max-age=0, s-maxage=60,
   stale-while-revalidate=300';

export const mediumPrivate =
  'private, max-age=30,
   stale-while-revalidate=120';

export const noStore =
  'no-store, no-cache, must-revalidate';
PLAIN ENGLISH

shortPublic — for catalog data and other read-only, operator-independent payloads. The CDN can keep one copy and serve every operator from it. 60s freshness, 5min grace.

mediumPrivate — for analysis payloads tied to a single operator. private keeps the CDN from sharing across users; only the browser caches it. 30s fresh, 2min stale-while-revalidate.

noStore — for finalize, evidence upload URL minting, anything that mutates or returns short-lived secrets. Never cached, never reused.

The naming rule: the policy name says who can share + how long. shortPublic is sharable; mediumPrivate is not. No reading the Cache-Control string to figure out the intent.

Nobody waits for the cold function

SWR means the user always gets a near-instant response from the edge. The freshness happens in the background. The trade: you might see a 105s-old number for 200ms. For a maturity score that changes once per finalize, that's invisible.

Which route gets which policy

GET /api/catalog shortPublic — same 100 questions for every operator. CDN serves one copy globally.
GET /api/assessments/[id]/analysis mediumPrivate — operator-scoped score JSON. Browser caches it for 30s; CDN never shares it across operators.
GET /api/assessments/trend mediumPrivate — longitudinal series for THIS operator's BU. Same isolation rule.
POST /api/assessments/[id]/finalize noStore — mutations are never cached. The response is also a fresh signature; serving an old one would be a bug.
POST /api/evidence/upload-url noStore — returns a 60s signed URL. Caching it would let one operator reuse another's upload window.

vercel.json — the static-asset side of the story

CODE · vercel.json 
{
  "headers": [
    {
      "source": "/assets/(.*)",
      "headers": [{
        "key": "Cache-Control",
        "value": "public, max-age=31536000, immutable"
      }]
    },
    {
      "source": "/index.html",
      "headers": [{
        "key": "Cache-Control",
        "value": "no-cache"
      }]
    }
  ]
}
PLAIN ENGLISH

Hashed assets get the year-long lock. Vite emits app.a3f2b71e.js; the filename changes when contents change, so caching forever is safe.

index.html stays no-cache. It points to the hashed assets. If the browser kept a stale index, the user would never see new code ship.

The pattern: immutable for content-addressed files, no-cache for the entry point. Same approach every fast SPA uses; we just spell it out in vercel.json so deploys are reproducible.
