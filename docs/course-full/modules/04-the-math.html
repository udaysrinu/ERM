How a score is born — pure math, no surprises.

Four functions. Two hundred lines. The entire patent moat. If anyone asks "how do you score?", this is the answer.

The score as a pour-over coffee

You can build a coffee shop where every barista pours by feel — different cup every time. Or you can build one where the recipe is exact: 22g coffee, 350ml water, 4-minute pour, 96°C. Same recipe → same coffee, every time, anywhere.

Our scoring engine is the second kind. The "recipe" is in shared/engines.ts. The "ingredients" are the operator's 100 answers. The "cup of coffee" is the overall maturity score — and the engine guarantees that the same answers always brew the same cup.

Function 1: computeVectors — the heart of the engine

CODE · shared/engines.ts:51 
export function computeVectors(responses) {
  // Step A — dimension averages
  for (const r of responses) {
    const q = QUESTIONS_BY_ID.get(r.questionId);
    dimSums.set(q.dimensionId, sum + r.score);
  }

  // Step B — pillar aggregates (weighted)
  for (const r of responses) {
    cellSums.set(key, sum + r.score * q.weight);
  }

  // Step C — overall = sum(pillarScore * pillarWeight)
  const overallScore = PILLAR_IDS.reduce(
    (sum, pid) => sum + pillarScores.get(pid) * PILLAR_WEIGHTS[pid], 0
  );

  return { pillarScores, dimensionScores, overallScore };
}
PLAIN ENGLISH

Take 100 answers in. Return 1 overall + 10 pillar + 4 dimension scores.

Step A: group answers by their dimension (People / Process / Technology / Governance) and average. This gives you 4 dimension scores.

Step B: for each pillar, weight each answer by how important that question is to that pillar, then sum. This gives you 10 pillar scores.

Step C: the overall score is a weighted average of the 10 pillar scores. Leadership matters more than Continuous Improvement, so its pillar weight is bigger.

Notice: no Date.now(), no random, no API calls, no database. Pure inputs in, pure output out. That's why it's reproducible.

Why "pure functions" is the patent moat

A pure function can't lie. There's no "hmm, last time it was Wednesday, this time it's Thursday, the answer might shift." We pinned this in tests: tests/engines.test.ts has 35 assertions like "these specific 100 answers must produce overall score 3.20." If anyone changes the math, that test fails. CI blocks the deploy. The reproducibility claim is enforceable in code, not in policy.
