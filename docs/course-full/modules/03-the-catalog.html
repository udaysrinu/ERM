The catalog — the product spec is data, not PowerPoint.

1,526 lines of TypeScript that encode 100 questions, 10 pillars, 4 dimensions, 4 benchmark profiles, and the standards-alignment receipts. Change one weight, watch the test suite catch it.

A musical score, not a slide deck

A symphony orchestra in Tokyo and one in Berlin can play the same Beethoven sonata and produce essentially the same piece — because they're both reading the same notation. The notation IS the spec.

Our catalog is the notation. shared/static.ts encodes every question, every weight, every benchmark — as data, not prose. The engine reads this data deterministically. Two runs of the same answers against the same catalog produce the same score, byte-for-byte.

You can't hash a slide deck. You can hash this. That's how the patent moat is enforceable — see Module 5 for the receipt mechanism.

The shape of the catalog

QUESTIONS 100 entries. Each: id, text, pillarId, dimensionId, weight, and a 5-level rubric of anchor text.
PILLARS 10 named risk domains: Leadership & Governance, Strategy & Integration, … Continuous Improvement.
PILLAR_WEIGHTS 10 numbers summing to 1.0. Leadership 0.20, Risk Assessment 0.20, Continuous Improvement 0.02. The "what matters most" knob.
DIMENSIONS 4 axes every question is tagged with: People, Process, Technology, Governance.
BENCHMARKS 4 reference profiles: Target / Industry / Peer / External. Each is a per-pillar target score the operator's score is compared against.
PILLAR_PROVENANCE Per-pillar standards alignment text — which clauses of ISO 31000, COSO ERM, NIST RMF, RIMS RMM each pillar maps to. Patent claim 13.
MATURITY_LEVELS 1=Initial, 2=Developing, 3=Defined, 4=Managed, 5=Optimized. The 1-5 scoring scale.

One question, fully encoded

CODE · shared/static.ts 
{
  id: 1,
  text: "Is there a formally approved ERM policy?",
  pillarId: "lead",
  dimensionId: "Governance",
  weight: 1.0,
  rubric: {
    1: "No formal policy exists.",
    2: "Draft policy circulates internally.",
    3: "Approved with annual review cadence.",
    4: "Integrated into ops; KPIs measure adherence.",
    5: "Continuously evolves; benchmarked against peers."
  }
}
PLAIN ENGLISH

id — primary key. The signature hash uses this to canonicalize responses (sorted by id).

text — what the operator literally sees on the questionnaire screen. Plain English, no jargon.

pillarId — foreign key into PILLARS. "lead" = Leadership & Governance.

dimensionId — one of the 4 axes. Drives the Focus Inspector tiles on Today.

weight — within its (pillar × dimension) cell, how much this question counts. Most questions are 1.0; a few are weighted heavier.

rubric — anchor text for each 1-5 score. The operator sees this as a tooltip and inline preview when they pick a score. Different per question.

The 4 benchmark profiles — what the score is compared against

🎯

Target

Where the operator wants to be — typically 4.0+ across the board. The "aspirational" benchmark.

🏭

Industry

Sector average. Drives the "is this normal for our industry" framing.

👥

Peer

Same-size, same-region competitors. Tighter than industry, more meaningful for boards.

🌐

External

Cross-industry leaders (e.g., what a high-maturity bank or hospital system looks like).

🔀
Switching benchmark is the only "live knob"

Every other input to the score is locked at finalize. The benchmark dropdown on Today (Target / Industry / Peer / External tabs) re-runs computeAnalytics against a different profile. The score doesn't change; only the gap and "aligned pillars" count do. Module 5 explains why this means the analysisHash changes but the scoringInputHash doesn't.

Provenance — the receipts for every weight

CODE · shared/static.ts 
PILLAR_PROVENANCE.lead = {
  weight: 0.20,
  standards: "ISO 31000 §5.4; COSO ERM 2017
    Component 1; NIST RMF Prepare step",
  rationale: "Leadership commitment is the
    precondition for every other pillar..."
};
PLAIN ENGLISH

weight: 0.20 — Leadership counts for 20% of the overall score.

standards — exactly which sections of which frameworks justify giving this pillar that much weight. Not "trust us" — citable references.

rationale — the human-readable argument. An auditor reads this and decides: do they accept the weighting?

This data is rendered verbatim on the Provenance screen. It's also embedded on PDF page 5. The product never abstracts the receipts away.

📜
Patent claim 13 lives in this field

Per-pillar and per-dimension standards-alignment provenance is one of the 24 patent claims. It's not a marketing line — every weight in the catalog has a citation. A competitor can't ship the same numbers without either copying our citations (legally fraught) or generating their own (which won't match ours when audited side-by-side).
