What we built — and why anyone should care.

A risk officer wants three numbers and a list. We built the boring infrastructure that makes those three numbers defensible.

The problem we're solving

Big companies hire consultants to assess their ERM maturity. A firm shows up with a spreadsheet, runs interviews for a quarter, hand-tallies scores, hands over a slide deck.

Three problems with that:

🎲

Non-reproducible

Two consultants score the same evidence differently. Two months apart, the same consultant produces a different score for the same company. The number isn't a measurement — it's an opinion.

📐

Non-comparable

"You scored 3.4." Compared to what? Industry? Peers? Last year's you? Without a benchmark you trust, the score is a vibe.

📅

Stale by delivery

A 90-day engagement produces a 60-day-old picture by the time the deck arrives. Risk doesn't wait for your slide cycle.

The product, in one sentence

🎯
ERM Navigator

A deterministic instrument that converts a 100-question, ISO/COSO/NIST-aligned interview into a reproducible weighted maturity score — with drift detection, sequenced roadmap, and a board-grade PDF, all in minutes.

Read that again with the right emphasis: deterministic instrument. Not a dashboard. Not a consulting deck. An instrument — like a thermometer. Same temperature → same number, every time, forever. That's the whole pitch.

What does a "thermometer" need to be one?

A thermometer can be trusted because it has three properties. So does our score:

reproducible Same inputs → same output, byte-for-byte. (Patent claim 24.)
standards-aligned Every weight is justified against ISO 31000, COSO ERM, NIST RMF, RIMS RMM. The receipts are public. (Patent claim 13.)
comparable-over-time Run it again 6 months later — what changed since last time, and by how much, with severity tags. (Patent claim 4.)

Everything in the codebase exists to deliver one of those three. If you can't tie a file to one of them, it's probably a UI shell or a polish layer.

03

The catalog — the product spec is data, not PowerPoint.

1,526 lines of TypeScript that encode 100 questions, 10 pillars, 4 dimensions, 4 benchmark profiles, and the standards-alignment receipts. Change one weight, watch the test suite catch it.

A musical score, not a slide deck

A symphony orchestra in Tokyo and one in Berlin can play the same Beethoven sonata and produce essentially the same piece — because they're both reading the same notation. The notation IS the spec.

Our catalog is the notation. shared/static.ts encodes every question, every weight, every benchmark — as data, not prose. The engine reads this data deterministically. Two runs of the same answers against the same catalog produce the same score, byte-for-byte.

You can't hash a slide deck. You can hash this. That's how the patent moat is enforceable — see Module 5 for the receipt mechanism.

The shape of the catalog

QUESTIONS 100 entries. Each: id, text, pillarId, dimensionId, weight, and a 5-level rubric of anchor text.
PILLARS 10 named risk domains: Leadership & Governance, Strategy & Integration, … Continuous Improvement.
PILLAR_WEIGHTS 10 numbers summing to 1.0. Leadership 0.20, Risk Assessment 0.20, Continuous Improvement 0.02. The "what matters most" knob.
DIMENSIONS 4 axes every question is tagged with: People, Process, Technology, Governance.
BENCHMARKS 4 reference profiles: Target / Industry / Peer / External. Each is a per-pillar target score the operator's score is compared against.
PILLAR_PROVENANCE Per-pillar standards alignment text — which clauses of ISO 31000, COSO ERM, NIST RMF, RIMS RMM each pillar maps to. Patent claim 13.
MATURITY_LEVELS 1=Initial, 2=Developing, 3=Defined, 4=Managed, 5=Optimized. The 1-5 scoring scale.

How a score is born — pure math, no surprises.

Four functions. Two hundred lines. The entire patent moat. If anyone asks "how do you score?", this is the answer.

The score as a pour-over coffee

You can build a coffee shop where every barista pours by feel — different cup every time. Or you can build one where the recipe is exact: 22g coffee, 350ml water, 4-minute pour, 96°C. Same recipe → same coffee, every time, anywhere.

Our scoring engine is the second kind. The "recipe" is in shared/engines.ts. The "ingredients" are the operator's 100 answers. The "cup of coffee" is the overall maturity score — and the engine guarantees that the same answers always brew the same cup.

Function 1: computeVectors — the heart of the engine

CODE · shared/engines.ts:51 
export function computeVectors(responses) {
  // Step A — dimension averages
  for (const r of responses) {
    const q = QUESTIONS_BY_ID.get(r.questionId);
    dimSums.set(q.dimensionId, sum + r.score);
  }

  // Step B — pillar aggregates (weighted)
  for (const r of responses) {
    cellSums.set(key, sum + r.score * q.weight);
  }

  // Step C — overall = sum(pillarScore * pillarWeight)
  const overallScore = PILLAR_IDS.reduce(
    (sum, pid) => sum + pillarScores.get(pid) * PILLAR_WEIGHTS[pid], 0
  );

  return { pillarScores, dimensionScores, overallScore };
}
PLAIN ENGLISH

Take 100 answers in. Return 1 overall + 10 pillar + 4 dimension scores.

Step A: group answers by their dimension (People / Process / Technology / Governance) and average. This gives you 4 dimension scores.

Step B: for each pillar, weight each answer by how important that question is to that pillar, then sum. This gives you 10 pillar scores.

Step C: the overall score is a weighted average of the 10 pillar scores. Leadership matters more than Continuous Improvement, so its pillar weight is bigger.

Notice: no Date.now(), no random, no API calls, no database. Pure inputs in, pure output out. That's why it's reproducible.

05

The receipts — making the patent moat tactile.

A pure function is reproducible. But the user can't see that without a signal. The "run signature" turns reproducibility into something an auditor can hold.

Like a chess game's PGN notation

In chess, every move history is a string: 1. e4 e5 2. Nf3 Nc6 .... Two players, anywhere in the world, can replay the exact same game from the notation. The notation IS the proof.

Our run signature is the same idea. It's a SHA-256 fingerprint of the inputs that produced a score. Two assessments with the same fingerprint MUST have produced the same score, because the math is deterministic and the inputs are bit-identical. The hash is the chess notation of an ERM score.

What goes into the signature?

responses 100 (questionId, score) pairs, sorted by id. Notes and evidence filenames are excluded — they don't change the score.
catalogHash Hash of the question catalog itself. If a question text changes or a weight is tweaked, this differs.
catalogVersion Human-readable bump (e.g. 1.0.0). Lets us evolve the catalog while keeping comparisons safe.
scoringSpecVersion Bumped when the scoring math itself changes. 1.0.0 today.
⚠️
Notice what's NOT in the hash

The current time. The operator's email. The browser. The IP address. The database row creation timestamp. None of those affect the score, so none of them belong in the signature. Including them would be lying to the auditor.

Why two hashes, not one?

CODE · shared/signatures.ts 
// Hash 1: the score itself
const scoringInputHash = sha256(canonicalize({
  responses: /* sorted, only q+s */,
  catalogHash, catalogVersion, scoringSpecVersion,
}));

// Hash 2: the analysis VIEW
const analysisHash = sha256(canonicalize({
  scoringInputHash,
  benchmarkType,           // target / industry / peer
  benchmarkProfile,        // the actual numbers
}));
PLAIN ENGLISH

Hash 1 — scoringInputHash — the fingerprint of "these answers, scored by these rules." It does NOT change when you switch benchmark.

Hash 2 — analysisHash — the fingerprint of "this score viewed against this benchmark." It DOES change when you toggle Target → Industry on Today.

This separation matters. An auditor can ask "did the score change between Q1 and Q2?" — answer: compare scoringInputHash. The analyst can ask "did the relative gap change?" — answer: compare analysisHash. Two questions, two receipts.

The contract is pinned in tests

The signature isn't a vibe — it's enforced by the test suite. tests/signatures.test.ts contains assertions that close the loopholes:

order-independence Shuffling the response array must not change the hash.
score-sensitivity Changing one answer must change the hash.
benchmark-isolation Switching benchmark changes analysisHash but NOT scoringInputHash.
coverage-rejection A response set with 99 valid + 1 fabricated questionId must reject.
range-rejection A score outside 1–5 (or non-integer) must reject.

If any of these break, CI fails the PR. The reproducibility claim is therefore enforceable: it's not a thing engineers promise, it's a thing tests check.

The questionnaire pipeline — 100 questions without losing your place.

A 100-question form is where most assessment products fail. Ours auto-resumes mid-session, uploads evidence inline, and never silently destroys progress.

A flight checklist that resumes mid-flight

Pilots have checklists. Each item gets ticked. If the pilot is interrupted, they go back to the last unticked item — they don't restart from the top, and they don't pretend an item was checked.

Our questionnaire is the same. The operator answers 100 questions across 10 pillars. They might get pulled into a meeting. They come back; the cursor is exactly where they left off. They click sidebar; nothing destroys their work. They upload a PDF; the upload happens inline without a "save" button.

The trick: lifted state with resume

Most React forms keep state inside the form component. When the user navigates away, the component unmounts, the state vanishes — work lost.

We lift the state to the App shell. The pipeline component is just a "view" of the draft. Mounting / unmounting doesn't destroy anything; the App holds the draft.

CODE · src/App.tsx 
// In App.tsx — survives screen changes
const [assessmentDraft, setAssessmentDraft] = useState({
  id: null,
  responses: {},
  notes: {},
  evidenceNames: {},
  evidencePaths: {},
  answeredAt: {},
});

// Passed down to the pipeline as props
<VectorCapturePipeline
  draft={assessmentDraft}
  onDraftChange={setAssessmentDraft}
/>
PLAIN ENGLISH

The App shell owns the draft. Even if the user navigates to Today and back, the App stays mounted — so the draft survives.

responses — questionId → score (1-5)

notes — questionId → free-text note

evidenceNames — questionId → filename string (always captured for audit trail)

evidencePaths — questionId → Storage object key (only set if upload succeeded). Module 9 covers this.

answeredAt — questionId → ISO timestamp. Captured but not yet surfaced in UI (claim 12, deferred).

A subtle bug Codex caught: batched setter race

In an early version of the lifted state, each setter spread the same stale draft:

BUGGY VERSION (caught pre-commit by Codex review) 
const setResponses = (next) => {
  onDraftChange({ ...draft, responses: next });
};
const setAnsweredAt = (next) => {
  onDraftChange({ ...draft, answeredAt: next });
};

// Caller fires both in one click handler:
setResponses(...);  // React batches
setAnsweredAt(...);  // stale draft! score lost
PLAIN ENGLISH

The bug: both setters captured draft at render time. React batches state updates; the second setter overwrites the first because both wrote against the same stale snapshot.

Symptom: the score literally got lost on every click. The timestamp saved; the score didn't.

Fix: use functional updates — onDraftChange((prev) => ({ ...prev, responses: next })). Each batched update reads the latest prev, so they compose correctly.

Why it matters: external review (Codex) caught this before commit. Reading your own code under deadline pressure misses these. Adversarial review > self-review.

⚠️
React state batching is a class of bugs you'll hit again

Whenever you have multiple setX calls in the same handler updating the same parent, prefer functional updates: setX(prev => …) instead of setX(newValue). The second form silently corrupts when batched.

A small UX win: the 2-pixel loading strip

Earlier versions blasted the whole screen with a "Computing..." overlay every time the operator switched BU or benchmark. Annoying for routine clicks.

We split loading into two states:

analysisLoading Fires on /api/assessments/[id]/analysis fetches. Shows a 2px terracotta progress strip ping-pong at the top of the screen. Non-blocking.
loading Reserved for genuinely user-blocking ops: login auth, assessment finalize. Full-screen "Computing" overlay still fires here — appropriate, because the user shouldn't keep clicking.

Lesson: not all loading is equal. Use a non-blocking indicator for routine fetches; reserve the blocking overlay for moments when blocking is the right behavior.

"Prior assessment" is operator-scoped — and that fact is the difference between an audit-grade product and a prototype

CODE · api/assessments/[id]/analysis.ts 
const [prior] = await sql`
  SELECT id FROM assessments
  WHERE "entityId" = ${assessment.entityId}
    AND id != ${id}
    AND "createdAt" < ${assessment.createdAt}
    AND status = 'completed'
    AND "operatorEmail" = ${assessment.operatorEmail}
  ORDER BY "createdAt" DESC LIMIT 1
`;
PLAIN ENGLISH

Find the previous version of THIS BU assessment, by THIS operator, that was actually finalized.

The operatorEmail filter exists for a real reason: without it, Operator B's drift headline could compute against Operator A's data. Caught during audit; shipped same day.

status = 'completed' excludes drafts. Drift only compares to finalized snapshots.

id != current prevents self-comparison (drift would be 0 across the board).

🚨
Cross-tenant data bleed: the silent killer

The original version of this query missed the operatorEmail filter. It looked harmless. It also silently leaked one operator's risk posture into another operator's headline. Multi-tenant SaaS lives or dies on this kind of filter.

The roadmap is a sort, not a stack of TODOs

CODE · shared/engines.ts:165 
export function generateRoadmap(pillarScores, benchmarkType) {
  const profile = BENCHMARKS[benchmarkType];
  const gaps = PILLAR_IDS.map(pid => ({
    pillarId: pid,
    gap: Math.max(0, profile[pid] - pillarScores.get(pid)),
  }));

  // score each canonical action by uplift / (cost × duration)
  const actions = ROADMAP_ACTIONS
    .filter(a => gapsByPillar.get(a.pillarId) > 0)
    .map(a => ({
      ...a,
      score: a.expectedUplift / (a.costScore * a.durationScore),
    }))
    .sort((a, b) => b.score - a.score);
}
PLAIN ENGLISH

Step 1 — find the gaps. For each pillar, how far below benchmark are we?

Step 2 — filter actions. The catalog has canonical improvement actions tagged by pillar. Drop ones targeting pillars that don't have a gap.

Step 3 — score by ROI. Each action has expectedUplift, costScore (1-5, lower=cheaper), durationScore (1-5, lower=faster). Priority = uplift ÷ (cost × duration). Cheap, fast, high-uplift wins.

Step 4 — sort and bucket. Top scorers Phase 1, next Phase 2, rest Phase 3.

Evidence — the audit-grade attachment story.

A score with no document behind it is hearsay. Real customers need real files in real storage with real access control.

A bank's safe-deposit box, not a public locker

The metaphor matters. We could have stored evidence in any old bucket and called it a day. We didn't. Every uploaded file lives in a private bucket, never publicly listable, accessible only via short-lived signed links our function issues per-request after verifying ownership.

The 5 properties that make storage audit-grade

private bucket No public listing. No public URL. The only way in is a signed link our function issues.
10 MB / file cap Server-side rejection of larger uploads — saves bandwidth, fits ERM evidence shape (PDFs, Excel, screenshots).
MIME allowlist PDF, XLSX, DOCX, common images, plain text. Bucket itself rejects anything else, regardless of file extension.
5-min signed URLs Download links expire in 300 seconds. Even if a link leaks via screenshare, it's stale by the time anyone tries.
deterministic key {assessmentId}/{questionId}-{filename}. One slot per (assessment, question). Re-uploads overwrite the slot.

The PDF — the score in an envelope you can mail.

A board doesn't open Vercel deployments. They open PDFs. The Report endpoint is the bridge from live app to durable artifact — same numbers, same provenance, same hash, in 5 pages.

A bank statement, not a screenshot

You don't audit a bank account by screenshotting the web UI. You audit it from the PDF statement — generated server-side, signed, archived. The PDF is the record of truth.

Our Report is built the same way. api/assessments/[id]/pdf.ts takes the same analysis JSON the Today screen reads, runs it through pdf-lib, and streams a binary back. No headless browser. No HTML scraping. Just data → bytes.

5 pages, each earns its place

Page 1 · Cover BU name, benchmark, overall score, run signature chip, generation timestamp. The chip is the receipt — same SHA prefix as the Today screen.
Page 2 · Live Brief Drift headline (regression / aligned / drifting) — the same string the Today hero shows. Deterministic, not LLM-generated.
Page 3 · Pillar table 10 rows: pillar · score · benchmark · gap · status. Sorted by gap descending so the worst pillars print at top.
Page 4 · Roadmap Top 14 actions sorted by uplift / (cost × duration). Phase pill, pillar, expected uplift. The same sort the Today table uses.
Page 5 · Provenance Per-pillar standards alignment — ISO 31000, COSO ERM, NIST RMF citations. Patent claim 13 in printable form.

Why pdf-lib instead of headless Chrome

⚡

Cold-start budget

A serverless function with headless Chrome cold-starts in 4-8s. pdf-lib cold-starts in <200ms. The Report button feels instant.

📦

Bundle size

Chrome binary + Puppeteer = ~170 MB. pdf-lib = ~600 KB. Fits the Vercel function size cap with room to spare.

🔒

Determinism

Same analysis JSON in → byte-identical PDF out. HTML-to-PDF rendering varies with font fallbacks, Chrome version, system locale.

⚖️

The trade-off

No CSS. Every layout decision — column x-coords, row heights, page breaks — is hand-coded. Worth it for the determinism + speed.

Edge and cache — the quiet 80% of "feels fast."

The score is deterministic. Which means the answer is cacheable. Which means we can make the second click feel free — without ever serving stale data to the wrong operator.

A library reading room, not a vending machine

A vending machine recomputes from scratch every time. A library hands you a copy from the shelf, and only goes to the basement when the catalog says the shelf is empty.

Our edge is the reading room. Vercel's CDN sits in front of every API route. The function tells it — per response — how long the answer is good for, who can share it, and whether to revalidate in the background. Module 5's hashes make this safe: the same input always produces the same output, so caching can never lie.

3 cache policies, named for what they actually do

CODE · api/_lib/cache.ts 
export const shortPublic =
  'public, max-age=0, s-maxage=60,
   stale-while-revalidate=300';

export const mediumPrivate =
  'private, max-age=30,
   stale-while-revalidate=120';

export const noStore =
  'no-store, no-cache, must-revalidate';
PLAIN ENGLISH

shortPublic — for catalog data and other read-only, operator-independent payloads. The CDN can keep one copy and serve every operator from it. 60s freshness, 5min grace.

mediumPrivate — for analysis payloads tied to a single operator. private keeps the CDN from sharing across users; only the browser caches it. 30s fresh, 2min stale-while-revalidate.

noStore — for finalize, evidence upload URL minting, anything that mutates or returns short-lived secrets. Never cached, never reused.

The naming rule: the policy name says who can share + how long. shortPublic is sharable; mediumPrivate is not. No reading the Cache-Control string to figure out the intent.

Nobody waits for the cold function

Which route gets which policy

GET /api/catalog shortPublic — same 100 questions for every operator. CDN serves one copy globally.
GET /api/assessments/[id]/analysis mediumPrivate — operator-scoped score JSON. Browser caches it for 30s; CDN never shares it across operators.
GET /api/assessments/trend mediumPrivate — longitudinal series for THIS operator's BU. Same isolation rule.
POST /api/assessments/[id]/finalize noStore — mutations are never cached. The response is also a fresh signature; serving an old one would be a bug.
POST /api/evidence/upload-url noStore — returns a 60s signed URL. Caching it would let one operator reuse another's upload window.

The pattern: immutable for content-addressed files, no-cache for the entry point. Same approach every fast SPA uses; we just spell it out in vercel.json so deploys are reproducible.
